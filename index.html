I
Setup · sixty seconds

Bind your own edition.

Choose a bundle, fill the project specification, set the toggles you actually want. The page produces a downloadable zip — opinionated rules, skills, memory, and workflows configured the way you'll use them.

i.Mode

Two paths through this page. Manual sets every toggle here; Discovery lets Claude inspect your project first and recommend.

Mode · Manual
Pick the toggles yourself.

Best when you already know the shape of the project. Every toggle gets resolved on this page.

Mode · Discovery
Let Claude audit first.

Claude inspects your repo, names the stack and structure, then proposes a bundle + toggle defaults. You confirm before anything's written.

ii.Bundle

Four shapes. Solo / personal is the loosest; Client / team is the strictest. The toggles below pre-fill from this choice.

  • № 01

    Solo · personal

    Single-author, single-machine projects. Aggressive auto-merge, lean PR ritual, full personal memory.

    Loosest
  • № 02

    Multi-dev · OSS

    Public or community-collaborative. Conservative PR rituals, CODEOWNERS, contributing surface.

    Open
  • № 03

    Confidential
  • № 04

    Client · team

    Strictest. Mandatory deep review, team-handoff notes, role-scoped isolation, full audit surface.

    Strictest

Toggle marker syntax

  
Sections inside template files are wrapped with HTML-style markers. When a toggle is off, the marker block is stripped from the output during binding.

  
<!-- TOGGLE:codeowners START -->
This text only appears if `codeowners` is ON.
<!-- TOGGLE:codeowners END -->

  
An :off suffix inverts the marker — the block appears only when the toggle is off. Useful for "the manual fallback when the automation isn't enabled" prose.

  
<!-- TOGGLE:auto_merge:off START -->
Without auto-merge, follow this manual checklist.
<!-- TOGGLE:auto_merge:off END -->

Process · what happens at setup

      
How the binding happens.

      
Two paths produce the same end state. The fast path is the in-browser binder above; the careful path is Claude executing SETUP.md against your repo.

    

  


  
The fast path · in-browser bind

  
    
    
  1. You pick toggles. The page tracks state in memory only — nothing transmitted.
    2. 
    
  2. You click Bind volume. The page fetches the template files from this domain, applies toggle filtering inline, and assembles a zip via JSZip.
    3. 
    
  3. Download fires. The zip lands as claude-code-templates-<bundle>-v18.zip.
    4. 
    
  4. You unzip at your project root. The bundle's CLAUDE.md, .claude/, optional .github/, and any other selected files appear in place.
    5. 
    
  5. You commit. Optional first commit: chore: install claude-code-templates v18 (bundle: 1-solo-personal).
    6. 
  


  
The careful path · paste to Claude

  
If you want a planning step before files land, copy the JSON config from Folio I and paste it into a fresh Claude Code session. Claude reads SETUP.md and walks four phases:


  
Phase 1 · Validate

  
Claude confirms your project name, repo, branch, and stack from the JSON. If anything's missing, a short interview fills the gaps. Empty toggles ("ask the user") get resolved in conversation.


  
Phase 2 · Plan

  
Claude writes the file list it's about to create, with bundle resolution and toggle-default expansion shown explicitly. You review before any file is written.


  
Phase 3 · Apply

  
Files land. Each one is created with toggle blocks resolved against your config. Existing files are never overwritten without explicit confirmation.


  
Phase 4 · Cleanup

  
If you used the fast-path zip, the claude-code-templates/ source folder can be deleted from your project root — only the rendered output is needed. Claude asks via the AskUserQuestion tool with three options: keep, delete-from-tree, or delete-from-git.


  
❦


  
Re-running setup

  
Setup is idempotent. Re-pasting the same JSON updates the toggle-resolved blocks in-place without disturbing your own edits — unless you've moved one of the template-controlled regions, in which case Claude pauses and asks.

The most expensive thing the rules prevent

  
One concrete moment — the receipt that earned the visual-slice rule.


  

    

      Two consecutive PRs on one visual feature, both abandoned
      2026-05-08
      ~3.1M output tokens burned
    

    

      
Across 4 sessions in a single day, two PRs attempted to land a complex visual subsystem as a single-PR MVP dump. Both were abandoned after burning ~3.1M output tokens chasing visual iteration that never settled. The entire design was eventually scrapped and replaced with a simpler approach.

      Rule that prevents the repeat: .claude/rules/visual.md — ship one verifiable slice at a time, with a debug toggle in place from line 1, and a pause before the next slice. Landed 4 days later as a direct retro.
    

  


  

    

      Largest single-session output burn
      2026-05-08
      1.12M out · 446 min · 27 files
    

    

      
One marathon session producing 1.12M output tokens, 4,128 lines added across 27 files. The token-efficiency "long-session signals" rule targets exactly this shape — when context is saturated, tool calls slow, and reads of the same file repeat, the rule says cut and start fresh.

      Rule that prevents the repeat: .claude/rules/token-efficiency.md § "Long-session signals → cut immediately"
    

  


  

    

      Highest tool-error session (friction signal)
      2026-05-08
      17 errors · 887K tokens
    

    

      
17 tool errors in one session. Each error is a wasted round-trip and a small context burn. Root causes typically: &&-chained Bash commands stalling on a partial permission deny, repeated reads of just-edited files, or hitting denied destructive commands without a fallback.

      Rule that prevents the repeat: memory feedback_atomic_bash_commands — one Bash call per logical step.

Caveats & methodology

    
    
      
  • Data source: per-session telemetry at ~/.claude/usage-data/session-meta/ (143 files) + facets/ (88 files). Earliest session 2026-04-06; latest 2026-05-12. Span: 36 days.
    • 
      
  • Project names anonymised as "project A" + "project B". Numbers + dates + rule names are real; no commit-author names, no client names, no repo URLs.
    • 
      
  • Pro→Max boundary detection: first date a single session exceeded 250K output tokens — was 2026-04-25. Pre-boundary max single-session output was 149,532. Post-boundary max jumps to 1.12M.
    • 
      
  • Rule-delta comparisons use 21-day windows before/after the rule landed. Token-volume deltas are confounded by project scope growth, so they're directional. Tool-errors-per-session is the cleaner signal.
    • 
      
  • All Pro projections are estimates. The Pro plan's 5-hour rolling window + message-count caps aren't modelled. Treat as directional, not exact.

About this edition.

      
A short note on where the templates came from, what's bundled, and how this site is maintained.

    

  


  
Where this comes from

  
These templates were extracted from two private projects — one consumer-software shop, one solo voxel-game build — across ~36 days of disciplined Claude Code work. Every rule, skill, and memory pattern bundled here was earned from a receipt: a specific moment where its absence produced a measurable cost. The receipts folio prints the most expensive of those moments verbatim.

  
The bundles are opinions, not standards. Solo · personal defaults aggressively because the cost of a wrong call is one developer's afternoon. Client · team defaults conservatively because the cost is a contract.

Privacy & data

  
This page runs entirely in your browser. No JSON, telemetry, or configuration is transmitted anywhere — the binder fetches template files from this domain and assembles the zip client-side via JSZip. No cookies, no analytics, no phone-home.


  
Maintenance

  
Solo-maintained as an open-source side project. Issues + pull requests welcome on a best-effort basis. The discipline behind the templates is the priority; this site exists to make it shareable.
