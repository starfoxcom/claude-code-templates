What Claude figures out Project & toggles.

In Discovery mode you only commit to mode (step 1), bundle (step 2), and optionally tools (step 4). Claude infers the rest from your codebase:

  1. Project metadata — name, repo URL, default branch, tech stack, license — from package.json / Cargo.toml / .git/config / existing LICENSE.
  2. Toggle overrides on top of the bundle defaults — e.g. if your repo is open-source it'll suggest contributing_md ON; if there's a paths-ignore-eligible workflow it'll suggest auto_merge ON. Universally-off toggles (specialised rules like clean_room_rule, dod_devlog_step) get promoted to ask so Claude evaluates whether your project fits them.
  3. Walks you through the proposal before any file is written. You confirm; files land.

Decision tree

        
Walk it top-down. The first answer that branches you out is your bundle.

        

          
Q1
Is anyone else committing to this repo?
If no → Solo · personal. If yes → Q2.

          
Q2
Is the repo public-facing?
If yes → Multi-dev · OSS. If private → Q3.

          
Q3
Is the work for a paying client under contract?
If no → Multi-dev · OSS (private mode). If yes → Q4.

          
Q4
Are you the only person on the engagement?
If yes → Client · solo. If no → Client · team.

        


        
No bundle wins. The right bundle is the one you'll actually follow.

Toggle marker syntax

        
Template files wrap toggle-controlled regions with HTML-style markers. When a toggle is off, the marker block is stripped at bind time.

        

          
marker syntax

          
<!-- TOGGLE:codeowners START -->
This text only appears if `codeowners` is ON.
<!-- TOGGLE:codeowners END -->

<!-- TOGGLE:auto_merge:off START -->
Without auto-merge, follow this manual checklist.
<!-- TOGGLE:auto_merge:off END -->

        

        
An :off suffix inverts the marker — the block appears only when the toggle is off. Useful for "the manual fallback when the automation isn't enabled" prose.

      


      
      

        

          
Process

          
How the binding happens.

          
Two paths produce the same end state. The fast path is the in-browser binder; the careful path is Claude executing SETUP.md against your repo.

        


        
The fast path — in-browser bind

        
    
          
  • You pick toggles. State lives in memory only — nothing transmitted.
    • 
          
  • You click Bind volume. The page fetches template files from this domain, applies toggle filtering inline, and assembles a zip via JSZip.
    • 
          
  • Download fires. Zip lands as claude-code-templates-<bundle>-v1.0.0.zip.
    • 
          
  • You unzip at your project root. The bundle's CLAUDE.md, .claude/, optional .github/, and any other selected files appear in place.
    • 
          
  • You commit. Suggested: chore: install claude-code-templates v1.0.0 (<bundle>).
    • 
        


        
The careful path — paste to Claude

        
Want a planning step before files land? Copy the JSON config from Folio I and paste it into a fresh Claude Code session. Claude reads SETUP.md and walks four phases:


        
Phase 1 · Validate

        
Claude confirms project name, repo, branch, and stack from the JSON. Missing fields get a short interview. Toggles marked "ask" get resolved in conversation.


        
Phase 2 · Plan

        
Claude prints the file list it's about to create, with bundle resolution and toggle-default expansion shown explicitly. You review before any file is written.


        
Phase 3 · Apply

        
Files land. Each one created with toggle blocks resolved against your config. Existing files are never overwritten without explicit confirmation.


        
Phase 4 · Cleanup

        
If you used the fast-path zip, the claude-code-templates/ source folder can be deleted from your project root — only the rendered output is needed. Claude asks via AskUserQuestion with three options: keep, delete-from-tree, or delete-from-git.


        
Re-running setup

        
Setup is idempotent. Re-pasting the same JSON updates toggle-resolved blocks in-place without disturbing your edits — unless you've moved one of the template-controlled regions, in which case Claude pauses and asks.

The most expensive thing the rules prevent

        
One concrete moment — the receipt that earned the visual-slice rule.

        

          

            
Two consecutive PRs on one visual feature, both abandoned
2026-05-08
~3.1M tokens burned

            
Across 4 sessions in a single day, two PRs attempted to land a complex visual subsystem as a single-PR MVP dump. Both were abandoned after burning ~3.1M output tokens chasing visual iteration that never settled. The design was scrapped and replaced with a simpler approach.
Rule that prevents the repeat: .claude/rules/visual.md — ship one verifiable slice at a time, with a debug toggle in place from line 1, and a pause before the next slice.

          

          

            
Largest single-session output burn
2026-05-08
1.12M out · 446 min · 27 files

            
One marathon session producing 1.12M output tokens, 4,128 lines added across 27 files. The token-efficiency "long-session signals" rule targets exactly this shape — when context is saturated, tool calls slow, and reads of the same file repeat, the rule says cut and start fresh.
Rule that prevents the repeat: .claude/rules/token-efficiency.md § "Long-session signals → cut immediately"

          

          

            
Highest tool-error session
2026-05-08
17 errors · 887K tokens

            
17 tool errors in one session. Each error is a wasted round-trip and a small context burn. Root causes: &&-chained Bash commands stalling on partial permission deny, repeated reads of just-edited files, hitting denied destructive commands without a fallback.
Rule that prevents the repeat: memory feedback_atomic_bash_commands — one Bash call per logical step.

  • All Pro projections are estimates. Pro's 5-hour rolling window + message-count caps aren't modelled. Treat as directional, not exact.

About this edition.

          
A short note on where the templates came from, what's bundled, and how this site is maintained.

        


        
Where this comes from

        
These templates were extracted from two private projects — one consumer-software shop, one solo voxel-game build — across ~36 days of disciplined Claude Code work. Every rule, skill, and memory pattern bundled here was earned from a receipt: a specific moment where its absence produced a measurable cost. The receipts folio prints the most expensive of those moments verbatim.

        
The bundles are opinions, not standards. Solo · personal defaults aggressively because the cost of a wrong call is one developer's afternoon. Client · team defaults conservatively because the cost is a contract.

Privacy & data

        
This page runs entirely in your browser. No JSON, telemetry, or configuration is transmitted anywhere — the binder fetches template files from this domain and assembles the zip client-side via JSZip. No cookies, no analytics, no phone-home.


        
Maintenance

        
Solo-maintained as an open-source side project. Issues + pull requests welcome on a best-effort basis. The discipline behind the templates is the priority; this site exists to make it shareable.
